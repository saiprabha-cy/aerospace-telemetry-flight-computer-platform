# ATFIDP Telemetry Protocol

## 1. Purpose

The ATFIDP telemetry protocol defines the binary packet generated by the embedded flight-computer software for transmitting flight-state information over UART.

The protocol is designed to provide:

- Fixed packet length
- Explicit synchronization
- Protocol versioning
- Sequence tracking
- Timestamp information
- Quantized flight parameters
- Flight-status reporting
- CRC-16 integrity verification

The current implementation produces and verifies a **22-byte telemetry packet**.

---

## 2. Packet Structure

```text
Byte Offset
   0        1        2        3        4        5        6
┌────────┬────────┬────────┬────────┬────────┬────────┬────────┐
│ Sync   │ Sync   │Version │ Sequence Number (32-bit)         │
│ 0x55   │ 0xAA   │  0x01  │        4 bytes, little-endian     │
└────────┴────────┴────────┴────────┴────────┴────────┴────────┘

Byte Offset
   7        8        9       10       11       12       13
┌────────┬────────┬────────┬────────┬────────┬────────┬────────┐
│        Timestamp (32-bit)         │ Temperature │ Altitude  │
│        little-endian              │    x10      │  x1       │
└────────┴────────┴────────┴────────┴────────┴────────┴────────┘

Byte Offset
  14       15       16       17       18       19       20       21
┌────────┬────────┬────────┬────────┬────────┬────────┬────────┬────────┐
│ Altitude │ Velocity x10 │ Battery x100 │Status│   CRC-16 little-endian │
│          │              │             │      │                        │
└────────┴────────┴────────┴────────┴────────┴────────┴────────┴────────┘
```

The actual field layout is:

| Offset | Size | Field | Encoding |
|---:|---:|---|---|
| 0–1 | 2 B | Sync | `0xAA55`, transmitted little-endian as `55 AA` |
| 2 | 1 B | Version | `0x01` |
| 3–6 | 4 B | Sequence | Unsigned 32-bit, little-endian |
| 7–10 | 4 B | Timestamp | Unsigned 32-bit seconds, little-endian |
| 11–12 | 2 B | Temperature | Unsigned 16-bit, °C × 10 |
| 13–14 | 2 B | Altitude | Unsigned 16-bit, metres × 1 |
| 15–16 | 2 B | Velocity | Unsigned 16-bit, m/s × 10 |
| 17–18 | 2 B | Battery Voltage | Unsigned 16-bit, volts × 100 |
| 19 | 1 B | Status | `0=OK`, `1=WARNING`, `2=CRITICAL` |
| 20–21 | 2 B | CRC-16 | CRC over bytes 0–19 |

**Total packet size: 22 bytes**

---

## 3. Byte Order

Multi-byte integer fields use **little-endian byte order**.

For example, the synchronization value:

```text
Logical value : 0xAA55
Byte 0        : 0x55
Byte 1        : 0xAA
```

A 32-bit sequence value is transmitted least-significant byte first.

Example:

```text
Sequence = 0x00000001

Byte order:
01 00 00 00
```

The same convention is used for:

- Sequence number
- Timestamp
- Quantized measurement values
- CRC-16

---

## 4. Field Encoding

Floating-point flight values are converted to unsigned integers before transmission.

This keeps the packet deterministic and avoids transmitting native C floating-point representations.

### Temperature

Temperature is scaled by 10.

```text
Encoded temperature = temperature_c × 10
```

Example:

```text
25.0 °C → 250 → 0x00FA
```

### Altitude

Altitude is represented in metres with a scale factor of 1.

```text
Encoded altitude = altitude_m × 1
```

Example:

```text
1000 m → 1000 → 0x03E8
```

### Velocity

Velocity is scaled by 10.

```text
Encoded velocity = velocity_mps × 10
```

Example:

```text
120.0 m/s → 1200 → 0x04B0
```

### Battery Voltage

Battery voltage is scaled by 100.

```text
Encoded battery = battery_v × 100
```

Example:

```text
24.00 V → 2400 → 0x0960
```

The current embedded implementation clamps negative values to zero during unsigned conversion.

---

## 5. Status Encoding

The flight-status field uses the following enumeration:

| Value | Status | Meaning |
|---:|---|---|
| `0` | OK | No monitored fault detected |
| `1` | WARNING | Warning-level condition detected |
| `2` | CRITICAL | Critical condition detected |

The status value is generated by the health-monitoring logic before telemetry serialization.

---

## 6. Sequence Number

The sequence field provides packet ordering information.

The embedded scheduler maintains a 32-bit sequence counter:

```text
Packet 0 → Sequence 0
Packet 1 → Sequence 1
Packet 2 → Sequence 2
...
```

The sequence number allows a receiving system to detect:

- Missing packets
- Repeated packets
- Unexpected packet ordering

The current implementation increments the sequence counter whenever a telemetry packet is constructed.

---

## 7. Timestamp

The timestamp represents elapsed flight-computer time in seconds.

The current STM32 implementation derives the timestamp from the HAL system tick:

```text
timestamp_s = HAL_GetTick() / 1000
```

The timestamp is transmitted as an unsigned 32-bit integer.

This provides a simple deterministic time reference for the current implementation. It is not intended to represent UTC or an absolute spacecraft time standard.

---

## 8. CRC-16 Integrity Check

The final two bytes contain a CRC-16 calculated over the first 20 bytes.

```text
CRC input:
bytes 0 through 19

CRC output:
bytes 20 and 21
```

The implementation uses:

```text
Initial value : 0xFFFF
Polynomial    : 0xA001
Processing    : LSB-first
```

The CRC algorithm is implemented in the embedded telemetry module and independently reproduced by the host-side Python verification script.

Conceptually:

```text
Telemetry Data
      │
      ▼
  Bytes 0–19
      │
      ▼
    CRC-16
      │
      ▼
  Bytes 20–21
```

During verification, the receiver recalculates the CRC and compares it with the transmitted value.

```text
Received CRC == Calculated CRC
              │
        ┌─────┴─────┐
        ▼           ▼
       PASS         FAIL
```

A CRC mismatch causes packet verification to fail.

---

## 9. Packet Verification

The embedded `telemetry_verify_packet()` function performs the following checks:

1. Buffer pointer is valid.
2. Packet length is exactly 22 bytes.
3. Synchronization bytes are correct.
4. Protocol version is supported.
5. Received CRC matches the calculated CRC.

```text
Incoming Packet
      │
      ▼
Length == 22?
      │
      ▼
Sync Valid?
      │
      ▼
Version Valid?
      │
      ▼
CRC Valid?
      │
 ┌────┴────┐
 ▼         ▼
PASS      FAIL
```

The current verifier does not implement a full receiver-side state machine, retransmission mechanism, or packet-loss recovery protocol.

## 10. Reference Packet

For the nominal flight-data state used by the embedded simulation:

```text
Temperature : 25.0 °C
Altitude   : 1000 m
Velocity   : 120.0 m/s
Battery    : 24.00 V
Status     : 0
Sequence   : 0
Timestamp  : 0 s
```

The resulting 22-byte packet is:

```text
55 AA 01 00 00 00 00 00 00 00 00 FA 00 E8 03 B0 04 60 09 00 18 13
```

The CRC bytes are:

```text
18 13
```

Interpreted as little-endian:

```text
CRC = 0x1318
```

## 11. Host-Side Verification

A Python verification utility is included in the firmware tools directory.

Its purpose is to provide an independent host-side check of the packet generated by the embedded implementation.

The verifier:

- Parses the binary packet
- Decodes the individual fields
- Recalculates CRC-16
- Compares received and calculated CRC values
- Reports the decoded flight data

Verified reference output:

```text
Telemetry Packet
----------------
Length     : 22 bytes
Sync       : 0xAA55
Version    : 1
Sequence   : 0
Timestamp  : 0 s
Temperature: 25.0 °C
Altitude   : 1000 m
Velocity   : 120.0 m/s
Battery    : 24.00 V
Status     : 0
CRC RX     : 0x1318
CRC CALC   : 0x1318

Telemetry verification: PASS
```

Python is used here as an **engineering verification tool**, not as the runtime language of the STM32 flight computer.

## 12. UART Transport

The telemetry packet is passed to the UART interface after successful packet construction and verification.

```text
Flight Data
    │
    ▼
Packet Construction
    │
    ▼
CRC Generation
    │
    ▼
Packet Verification
    │
    ▼
USART2
    │
    ▼
External Receiver
```

Current UART configuration:

| Parameter | Configuration |
|---|---|
| Peripheral | USART2 |
| Baud Rate | 115200 |
| Data Bits | 8 |
| Parity | None |
| Stop Bits | 1 |
| Flow Control | None |

The firmware calls the STM32 HAL UART transmission function to transmit the packet.

Physical UART electrical transmission has not been experimentally verified because physical STM32 hardware and an external UART receiver were not available during development.

## 13. Design Characteristics

The current telemetry protocol intentionally uses a simple fixed-length binary structure.

### Advantages

- Deterministic packet size
- Low serialization overhead
- Explicit field definitions
- Simple embedded implementation
- Easy host-side decoding
- CRC-based integrity verification
- Sequence tracking capability
- Straightforward extension through protocol versioning

### Current limitations

The protocol does not currently implement:

- CCSDS packet formatting
- Telecommand packets
- Authentication
- Encryption
- Retransmission
- Forward-error correction
- Packet fragmentation
- Dynamic payload lengths
- Time synchronization
- Radio-specific framing

These are outside the current implementation scope.

---

## 14. Protocol Extension Strategy

Future protocol changes should preserve backward compatibility where practical.

Potential extensions include:

```text
Version 1
   │
   ├── Existing flight telemetry
   │
   └── Fixed 22-byte packet

Future Versions
   │
   ├── Additional sensor fields
   ├── GPS data
   ├── IMU data
   ├── Mission state
   ├── Fault/event reporting
   └── CCSDS-compatible packetization
```

Any change to field layout, scaling, byte order, CRC behavior, or packet length should result in an explicit protocol-version update.

## 15. Verification Status

The telemetry implementation has been verified at the software level through:

- Embedded packet construction
- Packet-length validation
- Synchronization validation
- Version validation
- CRC generation
- CRC verification
- Host-side Python decoding
- Host-side CRC recalculation
- STM32 firmware compilation with zero errors and zero warnings

The nominal reference packet was independently decoded and verified with matching CRC values.

The physical UART transmission path remains unverified until the firmware is executed on STM32 hardware with a suitable UART receiver.

---

## 16. Summary

The ATFIDP telemetry protocol provides a compact binary interface between the embedded flight-computer software and a future telemetry receiver.

The complete processing chain is:

```text
FlightData
    │
    ▼
Quantization
    │
    ▼
Binary Serialization
    │
    ▼
CRC-16
    │
    ▼
22-Byte Packet
    │
    ▼
Packet Verification
    │
    ▼
USART2
    │
    ▼
Host / Ground Receiver
```

The current implementation establishes a deterministic and independently verifiable telemetry foundation while leaving the protocol open for future aerospace communication standards and hardware integration.
